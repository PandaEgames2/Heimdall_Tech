 Entregable 1 - Proyecto Final HEIMDALL TECH Documento de Especificación Técnica y Arquitectura de Datos (Versión Corregida) 1. Modelo de Desarrollo de Software (Scrum) Justificación Metodológica Se ha determinado el uso del marco de trabajo Scrum debido a la naturaleza evolutiva del proyecto HEIMDALL TECH. Scrum permite la entrega continua de valor mediante ciclos iterativos e incrementales (Sprints), facilitando la validación temprana de funcionalidades críticas como el registro vehicular offline y la integración paulatina del motor de Inteligencia Artificial. Backlog del Producto El Backlog del Producto consolida las capacidades centrales del sistema organizadas por bloques funcionales: Autenticación e Identidad: Control de acceso seguro y roles. Gestión Multi-cliente: Aislamiento de datos por establecimiento y planes comercializados. Base de Vehículos: Padrón centralizado de vehículos autorizados, responsables e historial. Registro Offline: Operatividad continua en dispositivos móviles sin dependencia de red. Reconocimiento con IA: Extracción de datos de placas mediante Visión por Computador. Planificación de Sprints Sprint 1: Plan Básico (Núcleo Operativo y Funcionalidad Offline) Autenticación e inicio de sesión de usuarios. Gestión de base de vehículos y responsables por establecimiento. Registro manual de movimientos (entradas y salidas). Almacenamiento local temporal y mecanismo de sincronización offline. Sprint 2: Plan Medio (Control Avanzado, Auditoría y Reportes) Gestión de roles dinámicos y asignación fina de permisos. Módulo de autorizaciones y marcado de vehículos restringidos. Registro y seguimiento de incidencias operativas. Generación de reportes estadísticos filtrables y auditoría de accesos. Sprint 3: Plan Avanzado (Integración de IA y Alertas en Tiempo Real) Integración del motor de IA para la extracción automática de placas desde fotografías. Comparación automatizada contra la base de datos centralizada. Sistema de alertas en tiempo real por coincidencia de placas restringidas o no registradas. 2. Requerimientos Funcionales (Atómicos y Secuenciales) Código Nombre Descripción Detallada RF-01 Autenticación de Usuario El sistema debe validar las credenciales de acceso (usuario y contraseña) para permitir el ingreso a la plataforma. RF-02 Gestión de Roles El sistema debe permitir la creación, edición y eliminación de roles dentro del sistema. RF-03 Asignación de Permisos El sistema debe permitir asociar un conjunto de permisos específicos a cada rol creado. RF-04 Gestión de Usuarios El sistema debe permitir registrar usuarios y asignarles un rol y un establecimiento específico. RF-05 Configuración de Establecimiento El sistema debe registrar los datos institucionales del establecimiento y vincularlo a un plan de servicio. RF-06 Registro de Vehículos El sistema debe permitir el registro de datos generales del vehículo (placa, marca, modelo, color). RF-07 Registro de Responsables El sistema debe permitir la vinculación de un responsable (propietario/residente) con un establecimiento y vehículo. RF-08 Registro de Movimientos El sistema debe registrar los eventos de entrada y salida de vehículos con su respectiva marca de tiempo. RF-09 Búsqueda Rápida El sistema debe permitir la consulta inmediata de vehículos registrados mediante la placa. RF-10 Consulta de Historiales El sistema debe mostrar el registro histórico de movimientos filtrado por fechas y vehículos. RF-11 Configuración de Autorizaciones El sistema debe gestionar el estado de autorización de ingreso para cada vehículo. RF-12 Marcado de Restricciones El sistema debe permitir clasificar vehículos como &quot;autorizados&quot;, &quot;visitantes&quot; o &quot;restringidos&quot;. RF-13 Registro de Incidencias El sistema debe permitir reportar eventos anómalos u observaciones operativas asociadas opcionalmente a un vehículo. RF-14 Cálculo de Tiempos El sistema debe calcular promedios de tiempo de permanencia dentro del establecimiento. RF-15 Reportes Estadísticos El sistema debe generar reportes exportables basados en filtros de tiempo, tipo de vehículo y movimientos. RF-16 Extracción IA de Placas El sistema debe procesar fotografías capturadas desde el dispositivo para extraer el texto de la placa mediante IA. RF-17 Comparación de Placas El sistema debe comparar la placa detectada por la IA con los registros existentes en la base de datos. RF-18 Generación de Alertas El sistema debe emitir una alerta sonora/visual al detectar una coincidencia de placa restringida o no autorizada. RF-19 Sincronización Offline El sistema debe almacenar los registros localmente cuando no hay red y sincronizarlos automáticamente al reconectarse. 3. Requerimientos No Funcionales RNF-01 Rendimiento: El sistema móvil debe responder en un tiempo menor a 1.5 segundos para lecturas locales, garantizando fluidez en dispositivos de gama baja. RNF-02 Compatibilidad: La aplicación móvil debe ser compatible con sistemas operativos Android desde la versión 7.0 (API nivel 24) en adelante. RNF-03 Usabilidad: La interfaz gráfica debe estar optimizada para el trabajo operativo en campo, con un flujo de trabajo de un máximo de tres pasos y botones con un área táctil mínima de 48x48 dp. RNF-04 Seguridad: Las comunicaciones entre cliente y servidor deben realizarse obligatoriamente mediante HTTPS/TLS 1.3, con contraseñas encriptadas mediante algoritmos fuertes (BCrypt). RNF-05 Privacidad: Cumplimiento estricto de las regulaciones de protección de datos personales; la información capturada no será compartida con terceros y se mantendrá de forma confidencial. RNF-06 Escalabilidad: La arquitectura debe diseñarse bajo el modelo SaaS en la nube, con capacidad de escalar horizontalmente ante el incremento de establecimientos y lecturas. RNF-07 Conectividad: La aplicación debe operar de forma totalmente funcional en entornos sin conectividad mediante el uso de almacenamiento local estructurado (SQLite/Room). RNF-08 Mantenibilidad: Separación clara y desacoplada de la arquitectura en capas: Frontend (Móvil), Backend (API RESTful) y Servicio de IA (Visión por Computador). 4. Diagrama de Casos de Uso (Correcciones Aplicadas) A continuación se detallan las correcciones estructurales aplicadas al modelo de Casos de Uso según las observaciones recibidas: Definición del Actor Externo: El Servicio IA (Visión por Computador) se clasifica explícitamente como un actor externo y se ubica fuera del límite ( boundary ) del sistema. Este servicio actúa como un proveedor de procesamiento fotográfico. Corrección de Relaciones ( <<extend>> vs <<include>> ): El caso de uso Procesar Foto con IA se ha redefinido como un flujo opcional. Por lo tanto, se vincula mediante una relación <<extend>> hacia los casos de uso Registrar Ingreso y Registrar Salida , eliminando la relación incorrecta de inclusión ( <<include>> ). Depuración de Casos de Uso Internos: Se eliminó el elemento &quot;Retornar placa candidata&quot; , determinando que corresponde a una respuesta técnica interna de la API de visión y no a una interacción de valor a nivel de caso de uso. 5. Diseño de Base de Datos (Código SQL DDL Corregido) El siguiente script DDL para MySQL Workbench implementa las correcciones relacionales solicitadas, garantizando el aislamiento por establecimiento, la unificación de movimientos y la flexibilidad en la captura con IA e incidencias.-- ============================================================================= -- ESQUEMA DE BASE DE DATOS: HEIMDALL TECH -- Motor: MySQL 8.0+ -- ============================================================================= DROP DATABASE IF EXISTS heimdall_db; CREATE DATABASE heimdall_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; USE heimdall_db; -- ----------------------------------------------------------------------------- -- TABLA: PLAN -- ----------------------------------------------------------------------------- CREATE TABLE PLAN ( id_plan INT AUTO_INCREMENT PRIMARY KEY, nombre VARCHAR(50) NOT NULL UNIQUE, descripcion TEXT, precio DECIMAL(10,2) NOT NULL DEFAULT 0.00, limite_usuarios INT NOT NULL DEFAULT 5, permite_ia BOOLEAN NOT NULL DEFAULT FALSE, estado BOOLEAN NOT NULL DEFAULT TRUE, fecha_creacion TIMESTAMP DEFAULT CURRENT_TIMESTAMP ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: ESTABLECIMIENTO -- ----------------------------------------------------------------------------- CREATE TABLE ESTABLECIMIENTO ( id_establecimiento INT AUTO_INCREMENT PRIMARY KEY, id_plan INT NOT NULL, nombre VARCHAR(100) NOT NULL, direccion VARCHAR(200) NOT NULL, telefono VARCHAR(20), estado BOOLEAN NOT NULL DEFAULT TRUE, fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_establecimiento_plan FOREIGN KEY (id_plan) REFERENCES PLAN (id_plan) ON DELETE RESTRICT ON UPDATE CASCADE ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: ROL -- ----------------------------------------------------------------------------- CREATE TABLE ROL ( id_rol INT AUTO_INCREMENT PRIMARY KEY, nombre VARCHAR(50) NOT NULL UNIQUE, descripcion VARCHAR(150) ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: USUARIO -- ----------------------------------------------------------------------------- CREATE TABLE USUARIO ( id_usuario INT AUTO_INCREMENT PRIMARY KEY, id_establecimiento INT NOT NULL, id_rol INT NOT NULL, nombre VARCHAR(100) NOT NULL, correo VARCHAR(100) NOT NULL UNIQUE, password_hash VARCHAR(255) NOT NULL, estado BOOLEAN NOT NULL DEFAULT TRUE, fecha_creacion TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_usuario_establecimiento FOREIGN KEY (id_establecimiento) REFERENCES ESTABLECIMIENTO (id_establecimiento) ON DELETE CASCADE ON UPDATE CASCADE, CONSTRAINT fk_usuario_rol FOREIGN KEY (id_rol) REFERENCES ROL (id_rol) ON DELETE RESTRICT ON UPDATE CASCADE ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: RESPONSABLE -- Aislamiento garantizado mediante asociación directa a ESTABLECIMIENTO. -- ----------------------------------------------------------------------------- CREATE TABLE RESPONSABLE ( id_responsable INT AUTO_INCREMENT PRIMARY KEY, id_establecimiento INT NOT NULL, nombre VARCHAR(100) NOT NULL, documento_identidad VARCHAR(20) NOT NULL, telefono VARCHAR(20), correo VARCHAR(100), departamento_unidad VARCHAR(50), CONSTRAINT fk_responsable_establecimiento FOREIGN KEY (id_establecimiento) REFERENCES ESTABLECIMIENTO (id_establecimiento) ON DELETE CASCADE ON UPDATE CASCADE, CONSTRAINT uk_responsable_doc_est UNIQUE (id_establecimiento, documento_identidad) ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: VEHICULO -- Unicidad de placa restringida por establecimiento. Se elimina campo 'estado'. -- ----------------------------------------------------------------------------- CREATE TABLE VEHICULO ( id_vehiculo INT AUTO_INCREMENT PRIMARY KEY, id_establecimiento INT NOT NULL, id_responsable INT NULL, placa VARCHAR(15) NOT NULL, marca VARCHAR(50), modelo VARCHAR(50), color VARCHAR(30), tipo_autorizacion ENUM('AUTORIZADO', 'VISITANTE', 'RESTRINGIDO') NOT NULL DEFAULT 'VISITANTE', fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_vehiculo_establecimiento FOREIGN KEY (id_establecimiento) REFERENCES ESTABLECIMIENTO (id_establecimiento) ON DELETE CASCADE ON UPDATE CASCADE, CONSTRAINT fk_vehiculo_responsable FOREIGN KEY (id_responsable) REFERENCES RESPONSABLE (id_responsable) ON DELETE SET NULL ON UPDATE CASCADE, CONSTRAINT uk_vehiculo_establecimiento_placa UNIQUE (id_establecimiento, placa) ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: MOVIMIENTO -- Unificación de Ingresos y Salidas en un solo modelo conceptual. -- ----------------------------------------------------------------------------- CREATE TABLE MOVIMIENTO ( id_movimiento INT AUTO_INCREMENT PRIMARY KEY, id_establecimiento INT NOT NULL, id_vehiculo INT NULL, -- Opcional: El vehículo podría no estar registrado previamente id_usuario INT NOT NULL, placa_leida VARCHAR(15) NOT NULL, tipo_movimiento ENUM('INGRESO', 'SALIDA') NOT NULL, fecha_evento DATETIME NOT NULL, id_dispositivo VARCHAR(100) NOT NULL, estado_sincronizacion ENUM('PENDIENTE', 'SINCRONIZADO') NOT NULL DEFAULT 'SINCRONIZADO', fecha_sincronizacion DATETIME NULL, CONSTRAINT fk_movimiento_establecimiento FOREIGN KEY (id_establecimiento) REFERENCES ESTABLECIMIENTO (id_establecimiento) ON DELETE CASCADE ON UPDATE CASCADE, CONSTRAINT fk_movimiento_vehiculo FOREIGN KEY (id_vehiculo) REFERENCES VEHICULO (id_vehiculo) ON DELETE SET NULL ON UPDATE CASCADE, CONSTRAINT fk_movimiento_usuario FOREIGN KEY (id_usuario) REFERENCES USUARIO (id_usuario) ON DELETE RESTRICT ON UPDATE CASCADE ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: RECONOCIMIENTO_PLACA -- Auditoría e historial de lecturas mediante la integración de IA. -- ----------------------------------------------------------------------------- CREATE TABLE RECONOCIMIENTO_PLACA ( id_reconocimiento INT AUTO_INCREMENT PRIMARY KEY, id_movimiento INT NULL, -- Opcional: Puede registrarse una lectura sin consolidar movimiento id_dispositivo VARCHAR(100) NOT NULL, id_usuario INT NOT NULL, url_fotografia VARCHAR(255) NOT NULL, placa_detectada VARCHAR(15) NOT NULL, nivel_confianza DECIMAL(5,2) NOT NULL, resultado_ia ENUM('COINCIDE', 'NO_COINCIDE', 'ALERTA') NOT NULL, fecha_procesamiento TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_reconocimiento_movimiento FOREIGN KEY (id_movimiento) REFERENCES MOVIMIENTO (id_movimiento) ON DELETE SET NULL ON UPDATE CASCADE, CONSTRAINT fk_reconocimiento_usuario FOREIGN KEY (id_usuario) REFERENCES USUARIO (id_usuario) ON DELETE RESTRICT ON UPDATE CASCADE ) ENGINE=InnoDB; -- ----------------------------------------------------------------------------- -- TABLA: INCIDENCIA -- Novedades registradas por el personal operativo. -- ----------------------------------------------------------------------------- CREATE TABLE INCIDENCIA ( id_incidencia INT AUTO_INCREMENT PRIMARY KEY, id_establecimiento INT NOT NULL, id_vehiculo INT NULL, -- Opcional: La incidencia puede ser ajena a un vehículo registrado id_usuario INT NOT NULL, titulo VARCHAR(100) NOT NULL, descripcion TEXT NOT NULL, nivel_prioridad ENUM('BAJA', 'MEDIA', 'ALTA', 'CRITICA') DEFAULT 'MEDIA', fecha_incidencia DATETIME NOT NULL, CONSTRAINT fk_incidencia_establecimiento FOREIGN KEY (id_establecimiento) REFERENCES ESTABLECIMIENTO (id_establecimiento) ON DELETE CASCADE ON UPDATE CASCADE, CONSTRAINT fk_incidencia_vehiculo FOREIGN KEY (id_vehiculo) REFERENCES VEHICULO (id_vehiculo) ON DELETE SET NULL ON UPDATE CASCADE, CONSTRAINT fk_incidencia_usuario FOREIGN KEY (id_usuario) REFERENCES USUARIO (id_usuario) ON DELETE RESTRICT ON UPDATE CASCADE ) ENGINE=InnoDB;
